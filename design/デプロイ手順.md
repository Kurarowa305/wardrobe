# デプロイ手順

## 1. 目的

通常のデプロイは `.github/workflows/terraform.yml` によりmasterへのpushで AWS `dev` 環境へ反映する。以下の手動操作例は障害対応の参考で、通常作業では実行せず、既存の承認・運用に従う。

## 2. 前提

- 実行ディレクトリはリポジトリルート（例: `/home/oyadomaritaiki/projects/wardrobe`）
- AWS 認証が済んでいること（`aws sts get-caller-identity` が成功すること）
- `pnpm install --frozen-lockfile` が成功すること
- 対象リージョン: `ap-northeast-1`
- 対象 Terraform 変数ファイル: `infra/terraform/env/dev.tfvars`

初期確認:

```bash
cd /home/oyadomaritaiki/projects/wardrobe
export AWS_REGION=ap-northeast-1
# 必要なら export AWS_PROFILE=<your-profile>
aws sts get-caller-identity
pnpm install --frozen-lockfile
```

## 3. 手動デプロイ手順

### 3.1 初回のみ: bootstrap（tfstate バケット作成）

`tfstate` バケットが未作成の場合のみ実行する。

```bash
cd infra/terraform/bootstrap
terraform init
terraform plan \
  -var='env=dev' \
  -var='region=ap-northeast-1' \
  -var='name_prefix=wardrobe-dev-'
terraform apply \
  -var='env=dev' \
  -var='region=ap-northeast-1' \
  -var='name_prefix=wardrobe-dev-'
cd ../../..
```

### 3.2 Lambda パッケージ作成

```bash
bash infra/terraform/app/scripts/package-lambda.sh
```

### 3.3 Terraform(app) 反映

```bash
cd infra/terraform/app
terraform init
terraform workspace select dev || terraform workspace new dev
terraform plan -var-file=../env/dev.tfvars
terraform apply -var-file=../env/dev.tfvars

WEB_BUCKET_NAME=$(terraform output -raw web_bucket_name)
WEB_DIST_ID=$(terraform output -raw web_cdn_distribution_id)
WEB_CDN_DOMAIN=$(terraform output -raw web_cdn_domain)
API_ENDPOINT=$(terraform output -raw api_endpoint)
IMAGES_CDN_DOMAIN=$(terraform output -raw images_cdn_domain)
WEB_TOP_URL="https://${WEB_CDN_DOMAIN}/"
cd ../../..
```

### 3.4 Web 配信反映（S3 sync + CloudFront invalidation）

```bash
NEXT_PUBLIC_API_BASE_URL="${API_ENDPOINT}" \
NEXT_PUBLIC_IMAGE_PUBLIC_BASE_URL="https://${IMAGES_CDN_DOMAIN}" \
NEXT_PUBLIC_ENABLE_MSW="false" \
pnpm --filter web build
aws s3 sync apps/web/out s3://${WEB_BUCKET_NAME}
aws cloudfront create-invalidation --distribution-id "${WEB_DIST_ID}" --paths "/*"

echo "Top page URL: ${WEB_TOP_URL}"
echo "API endpoint: ${API_ENDPOINT}"
echo "Images CDN domain: https://${IMAGES_CDN_DOMAIN}"
```

## 4. デプロイ後確認

- `WEB_TOP_URL` にアクセスし、トップページが表示されることを確認
- `API_ENDPOINT` への疎通確認
- 必要に応じて CloudWatch Logs / API Gateway / CloudFront のメトリクスを確認

## 5. 運用上の注意

- プロジェクト方針では `terraform apply` は CI 実行が原則。
- 手動 `apply` は障害対応や検証など、例外時のみ実行する。
- Terraform state は S3 backend を使用し、同時 `apply` を避ける。

## 共有天気API #280 の運用

1. 既存 `TABLE_NAME` / `AWS_REGION` を使用する。ローカルのみ `DDB_ENDPOINT` を利用。無料Open-Meteo接続にはAPIキーを追加しない。送信先はコード固定の `https://api.open-meteo.com/v1/forecast`、Best Match・JST・日次4項目・当日のみ。商用化は#274の利用条件を再判断する。
2. 先にTerraform差分を反映する。`GET /wardrobes/{wardrobeId}/weather` はwardrobe Lambda、TTL属性は `ttl`。API内部10秒を応答する余裕のためLambda実行上限を最低12秒とする。既存wardrobe/template IAMは同テーブルのGetItem/UpdateItemを許可しており、追加サービス権限は不要。
3. CloudWatchで `weather_provider_usage_80_percent` を監視する。provider USAGEのrevision・gateUntil・各窓の利用量、APIの503/遅延も確認する。100%では新規外部送信を止め、既存当日cache・手動推薦を継続する。quota増加・ゲート削除による自動復旧は行わない。
4. 429は最低5分または有効なRetry-Afterまで全地域を停止する。キーごとの失敗は5分抑止。明示更新もその期限を守る。予約失敗/DB障害では外部送信しない。共有使用量にTTLを付けたり、障害対応でカウンターを初期化したりしない。
5. ロールバックは前のLambda成果物・APIルートへ戻す。STATEの期限付き項目は残してよい。履歴操作記録にはTTLがないため、天気TTL導入で履歴の再送保証を削除しない。CIの固定fixtureは実予報の精度確認ではない。

## ホーム改修の切替・監視・復旧（#284）

### 切替前と反映順

1. PRの対象SHAでGitHub Actions CI、独立レビュー、ブランチルールを確認する。`CI`と`Terraform`は別workflowであり、現在のTerraformはmaster pushで起動する。追加の本番環境・有料契約を作成しない。
2. 既存Terraform workflowはplan→apply→Webの順に実行する。applyは`wardrobe-dev-terraform`で直列化される。APIルート（地域・天気・テンプレート推薦）、Lambda最低12秒、同梱辞書、DynamoDB `ttl`、既存5GSIを確認してから新Webを配信する。
3. 追加データは後方互換。旧METAの地域は0/null、旧template revisionは0。既存履歴・服・画像を移行/削除する必要はない。`Idempotency-Key`は既存CORSの`allow_headers=["*"]`で許可される。
4. Web buildはMSW無効でAPI/画像CDN URLを渡す。配信後は地域設定、手動推薦、確認キャンセル、記録と履歴削除、PWA起動、画像と出典ダイアログを対象環境で確認する。CIのfixture検証は実環境や実予報精度の確認を代替しない。

### 観測対象

- CloudWatch Logsの`weather_provider_usage_80_percent`を検索する。wardrobe（天気）とtemplate（auto推薦）の両Lambdaが発行し得る。ログ保持は14日。監視イベントの発行を実装しているが、通知先付きAlarm/SNSを自動構築したわけではない。
- provider USAGEの件数・gateUntil、外部503とAPI遅延、`REGION_CHANGED`/`TARGET_DATE_CHANGED`、DB読取期限、未処理キーを確認する。100%上限時は新規送信停止、当日cacheと手動推薦を使用する。
- 出典表示は天気状態にかかわらず情報アイコンから確認できる。Open-Meteo / CC BY 4.0、デジタル庁ABR / PDL1.0、加工と独自指数の説明・リンクを配信物で確認する。利用条件は#274の判断を引き継ぐ。

### 復旧時に保持するもの

Webのみ戻す場合も、確認記録を受け付けたAPIの再送互換性は維持する。履歴操作記録・deletedAt墓標・各端末の未確定操作を消去しない。旧APIへ全面的に戻すと再送保証を失うため、記録開始後のAPI復旧は操作記録対応を含む成果物を選ぶ。

天気STATEの論理期限を尊重し、前日/別地域cacheを手動で延命しない。USAGEの初期化・429ゲート解除で利用枠を回避しない。地域辞書更新、商用契約、監視通知先追加は今回のリリース操作には含めない。
