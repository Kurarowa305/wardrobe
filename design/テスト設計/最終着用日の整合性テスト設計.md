# 最終着用日の整合性テスト設計（#278）

## 実行とCI

- `pnpm --filter api test:wear-stats-integrity`
- `pnpm --filter api test:wear-stats-audit`

両方をAPIの `test` と `.github/workflows/ci.yml` に組み込む。外部サービス、認証、時刻に依存しない。

## 検証する境界

整合性テストは実際の履歴usecase、服・テンプレート・履歴repo、日別件数repo、DynamoDBクライアントを通し、SDKの送信先だけをメモリ内ストアに差し替える。ストアは使用する条件式・更新式を評価し、全操作をコピーに適用して成功時のみコミットする。未対応の構文は失敗させる。再計算のQueryで強整合指定が欠けると空の古い読み取りを返し、指定漏れを検出する。

これはAWS実接続・DynamoDBサービスの構文実行検証ではない。履歴更新ロジック、渡す条件式、強整合フラグ、全件ロールバックを検証する。実データの整合性は別途読み取り監査が必要。

## 整合性ケース

1. 服の組合せ記録：全服の統計と日別件数を更新し、同日2件の1件削除で最終着用日を保持。過去日追加で後退せず、最新日の最後の削除で前日へ、全件削除で0へ戻る。
2. テンプレート記録：上記をテンプレートと全構成服について検証。
3. 服の編集：記録作成前に読んだ値で後から通常編集しても、更新済み統計・索引を保持する。
4. テンプレート編集：同じ競合を検証する。
5. 過去日検索：強整合の読み取りをSDKへ渡し、既存の過去日を再計算に反映する。
6. 件数が元へ戻る競合：最新日削除の再計算後に過去日追加・別日削除を実行。古いトランザクションを拒否し、履歴・日別件数・統計の全件が変化しない。
7. 同じ読取結果からの並行作成：片方だけ成功。更新番号未付与の既存項目でも競合を検出する。
8. 同日の最後の削除と新規追加：先に追加が完了した場合、古い削除でその日を消さない。読み直して削除すると1件分が残る。
9. 日別件数の欠落：CONFLICTになり履歴も統計も変化しない。
10. 未来日・共有服・構成変更：未来日の最終着用日を扱え、テンプレート編集後の履歴削除でも記録時の全構成服を戻す。
11. 作成・削除handler：実際に並行記録を挟み、統計の条件失敗をCONFLICTへ変換する。アプリケーションによる再送は1回も発生しない。

全状態の確認では着用回数、最終着用日、2つの索引キー、日別件数の合計と正数性を検査する。初回再現ではケース1〜6が失敗し、修正後に成功した。

## 監査ケース

正常データ、同日削除による最終日0、日別件数の誤り・欠落・余分な行、未着用対象、論理削除済み対象、構成服のない旧履歴、対象不存在、同一キー重複、不正件数、不正日付を検証する。入力順に依存しない指紋、CLIのJSON出力・不一致時の終了コード2・既存レポート上書き拒否も確認する。

## 既存テストの更新

通常編集repoの期待値を統計保持へ変更。API-16の同日2件のfixtureは前日へ戻す旧期待値を同日保持へ変更し、再計算呼び出しは同日の最後の1件のみとする。トランザクションビルダーの期待条件に最終着用日と更新番号を追加する。
