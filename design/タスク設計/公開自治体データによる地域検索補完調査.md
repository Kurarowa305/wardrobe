## 1. 結論

デジタル庁のアドレス・ベース・レジストリ（以下ABR）を採用する。名称・読みの市区町村マスターと代表座標の市区町村マスター位置参照を、6桁の全国地方公共団体コードで結合して、バージョン固定の検索辞書を同梱する。ABRは行政が保有する住所データを基に整備され、都道府県・市区町村・町字を階層化している。[デジタル庁の説明](https://www.digital.go.jp/policies/base_registry_address)

補完の実装案は、地域の候補検索をABR辞書へ統一し、選択済み代表座標で天気だけをOpen-Meteoから取得する。Open-Meteo Geocodingの結果とABRの候補を同じランキングへ混ぜると、自治体と施設の混在、重複、保存IDと出典の分岐が残るため、混合しない。これはwardrobe側で採用した設計方針である。

取得したABRの1,918行は名称・座標が全件結合でき、読みの欠損もなかった。かな、同名市、政令市区を含む23入力の検索試作が通った。ただし、2026年の最新全国自治体一覧との全件照合は未実施であり、取得件数だけから全国最新・完全とは結論しない。[固定証拠](../調査データ/japan-municipality-274/manifest.json)、[検証スクリプト](../../scripts/check-japan-municipality-274-evidence.py)

### 最新性の留保

[市区町村カタログの保存値](../調査データ/japan-municipality-274/city-catalog.json)は説明上の最終更新日が2024-03-12、取得HTTPヘッダーも2024年を示す。取得が2026年でも「2026年最新版」とは呼ばない。デジタル庁サイト全体の更新日、町字正式版の公開日、市区町村ファイル自体の更新日は区別する。[デジタル庁の整備状況](https://www.digital.go.jp/policies/base_registry_address)

ABRには浜松市の現行3区（中央区・浜名区・天竜区）が入っていた。一方、比較したlocalgovjpは1,916行で浜松市の旧7区が残り、コード集合はABRにだけ9件、localgovjpにだけ7件あった。localgovjpはCC0で扱いやすいが、READMEの2026年更新履歴は自治体URLの更新であり、自治体名称・区構成が最新という根拠にはならない。[提供者README](https://github.com/code4fukui/localgovjp)、[比較対象の固定JSON](../調査データ/japan-municipality-274/localgovjp.json)

この差分も踏まえてABRを採用する。全国最新一覧との全件照合は未実施だが、ユーザーは今回の検証範囲でよいと了承した。追加照合を採用・#274完了の条件にしない。現在の固定辞書を使用し、将来の改廃対応は更新機能とともにbacklogへ分離する。

## 3. 日本語・かな検索の試作

[試作結果](../調査データ/japan-municipality-274/search-prototype-results.json)では、次の23入力で期待するコードを上位10件に含むことを確認した。本番検索の性能・UX検証ではない。

| 確認対象 | 入力例・結果 |
| --- | --- |
| 漢字・ひらがな・カタカナ・半角 | 新宿区 / しんじゅく / シンジュク / ｼﾝｼﾞｭｸ → `131041` |
| 読みが必要な村 | 檜原村 / ひのはら → `133078` |
| 接尾辞なし | 札幌 / さっぽろ、那覇 / なは |
| 同名自治体 | 府中市 / ふちゅう → 東京都`132063`と広島県`342084`の両方 |
| 都道府県での絞り込み | 東京都 府中 / とうきょうと ふちゅう / 広島県府中市 |
| 政令市区 | 横浜市中区 / 横浜 中区 / よこはましなかく、浜松市浜名区 / はままつしはまなく |
| 1文字自治体・町村 | 津、白馬村、びえい |

追加確認では「中区」は複数候補、「東京」は10件超となり、上位10件で打ち切る。「浜松市中区」は0件、空入力・存在しない自治体も0件だった。[検証コード](../../scripts/check-japan-municipality-274-evidence.py)

実装案は次のとおり。

- 入力をNFKCで正規化し、カタカナをひらがなへ揃える。辞書にある名称と読みから別名を生成する。一般的な漢字の読み推測やローマ字検索は今回の対応範囲に含めない。
- 漢字の行政接尾辞を除いた別名は持つが、かなの末尾を機械的に1文字削らない。「なは」を誤って「な」に縮めない。
- 空白・カンマ区切りは各語が一致する候補に絞る。完全一致、前方一致、部分一致の順、同順位は自治体コードの順で安定させる。
- 1文字入力も受け付ける。「津」を外部Geocodingの文字数制限に合わせて拒否しない。空入力・64文字超は検索せず入力状態を返す。
- 表示は都道府県・郡・市・区を含む名称とし、政令市区は「神奈川県横浜市中区」のように親市を省かない。候補上位10件と`hasMore`を返し、件数上限を全件と誤認させない。
- 同名市も先頭候補を自動採用しない。検索ボタン／IME確定後Enter → 候補選択 → 保存という#277の合意を維持する。

## 4. 代表座標と天気APIへの接続

ABR取得値は全行`EPSG:6668`（JGD2011）であり、WGS84そのものと呼ばない。日本の測地系の背景は[国土地理院](https://www.gsi.go.jp/sokuchikijun/datum-main.html)、ABRのデータ構造は[デジタル庁の公開データ構成](https://www.digital.go.jp/policies/base_registry_address)を参照する。精密な座標変換や全国の誤差量の検証は今回行っていない。

天気の自治体代表地点という用途では、原SRIDを保持した上で緯度・経度を近似利用する案とする。近似利用の方針を`jgd2011-as-wgs84-weather-v1`として記録し、将来の変換方針変更と区別する。これはwardrobeの提案であり、測地系が同一という主張でも、全国で気象格子が変わらないことの保証でもない。[Open-Meteoの緯度・経度指定](https://open-meteo.com/en/docs)

新宿区`131041`（35.69389, 139.703463）と檜原村`133078`（35.72684, 139.148852）でABR座標をそのまま渡し、`start_date=end_date=2026-10-11`、`timezone=Asia/Tokyo`、Best Matchの日次4変数を取得した。両方HTTP 200、当日の4項目が数値で返った。[接続証拠](../調査データ/japan-municipality-274/forecast-from-abr.json)

この確認は2地点の接続性と当日指定の証拠であり、全自治体・離島の成功率や予報精度を示さない。応答の座標はモデル格子へ移るため、ABRの保存代表座標を予報応答で上書きしない。代表地点は自治体全域、特に山間部や離島の天候を代表しきれない。

## 5. 識別子・保存・固定辞書の確定方針

検索候補IDは`abr:lg:{6桁コード}`とし、先頭ゼロを保持する。クライアントから受けたIDをサーバーの同梱辞書で再解決し、有効コード・名称・座標を検証して保存する。クライアント申告の座標を信用しない。Open-Meteo GeocodingのIDとは別名前空間とする。

保存する情報は`source=abr`、6桁コード、表示名・行政階層、`latitude`、`longitude`、`sourceSrid`、`coordinatePolicy`、`datasetVersion`（取得日＋SHA-256）、`resolvedAt`、地域変更`revision`。同じ地域・座標・JST日の天気を当日中再利用し、地域変更と日付変更に追随できる契約とする。具体的DTOと物理保存先は#276で決める。

個人利用で地点修正の機会が少ないため、初回の固定辞書を同梱し、**辞書更新機能・月次更新確認は今回は導入しない**。[backlog優先度C](backlog.md)に将来の更新機能を記録した。辞書版・出典・SHAは初回データの識別用に保持する。未知コードは再検索を案内し、任意の座標や別地域を黙って採用しない。

将来の更新機能を扱う際には、取得・検証失敗時の旧版維持、名称と座標の全件結合、前版との改廃・座標差分、既存保存地域への影響を検討する。これらの更新処理を#280／#282の今回の実装条件には含めない。

## 6. ライセンスと出典ダイアログ

2026-05-29更新の[ABR利用規約](https://www.digital.go.jp/policies/base_registry_address_tos)は特記がないコンテンツへPDL1.0を適用し、出典と編集・加工の主体の表示を求める。一方、取得した[カタログ](../調査データ/japan-municipality-274/city-catalog.json)の`licenseInfo`はCC BY 4.0を指す。[PDL1.0](https://www.digital.go.jp/resources/open_data/public_data_license_v1.0)はCC BY 4.0との互換性を明示するため、どちらかの表記を無視せず、提供元・元データ・規約リンク・加工表示を残す案とする。

出典を付した辞書の複製・加工・同梱と選択地域の永続保存に利用できると判断する。ABRの商用利用可能性とOpen-Meteo無料APIの非商用条件は別であり、天気API側の条件は既存調査を維持する。[PDL1.0](https://www.digital.go.jp/resources/open_data/public_data_license_v1.0)、[Open-Meteo利用条件](https://open-meteo.com/en/terms)

> 地域データ: デジタル庁「[アドレス・ベース・レジストリ](https://www.digital.go.jp/policies/base_registry_address)」市区町村マスター・市区町村マスター位置参照・都道府県マスターをwardrobeが結合・検索用に加工。[利用規約](https://www.digital.go.jp/policies/base_registry_address_tos)（PDL1.0、取得カタログはCC BY 4.0）。データ取得日: 2026-10-11。

## 7. 後続に残す事項

#276ではABR候補・保存契約、原SRIDと近似方針、固定辞書の版と未知コード、地域変更時のキャッシュと保存地域の扱いを具体化する。#279 / #282では辞書生成・サーバー再解決・候補選択・出典ダイアログを実装し、#284では同名・かな・1文字・未知コード・打切りを検証する。辞書更新とそれに伴う改廃処理はbacklog優先度Cへ分離する。

今回の検証は固定データと検索試作・2地点の接続に限る。残る主なリスクは、全国最新一覧との全件照合が未実施であること、座標の精密変換・全国の予報精度が未検証であること。ユーザー了承により追加調査を完了条件にしない。辞書は取得した行を保持し、予報を取得できない地域も通常の取得失敗と同じ扱いとする。採用判断の完了と本番機能実装を区別する。
