# ホーム地域検索ダイアログの実現方法調査

調査日: 2026-10-09。対象: #277 / Q5。公式資料と現行コードの調査のみ。認証情報を使う実接続・契約・課金操作は行っていない。

## 結論と判断範囲

ホーム上で市区町村名を検索し、行政区域付きの候補から選ぶダイアログは、QWeather GeoAPI とアプリのバックエンドを介して構成できる。日本の全市区町村、読み仮名、同名地名の検索品質までは公式資料だけでは保証できない。#273 の接続検証で実データを確認する。

ユーザー合意は「ホーム上の検索ダイアログ」「変更を確定する前に閉じれば元の地域を維持」。以下の検索タイミング・保存操作・API境界は実装候補であり、#274 の運用判断、#276 の契約・物理データモデルを確定するものではない。

## 公式仕様から確認できたこと

| 項目 | 確認結果と適用案 |
| --- | --- |
| 検索 | `GET /geo/v2/city/lookup`。必須 `location` は地名・地点ID・座標に対応。`range=jp` で日本に絞り、`lang=ja`、`number=10` を初期案とする。`number` は1〜20、既定10。`adm` で上位行政区域による絞り込みが可能。[City Lookup](https://dev.qweather.com/en/docs/api/geoapi/city-lookup/) |
| 候補表示 | `id` を識別子とし、`name` と `adm1` / `adm2` を候補に表示する。同じ表示文字列は重複させない。行政区階層を「必ず都道府県・市」の固定構造とみなさず、実レスポンスで確認する。[City Lookup](https://dev.qweather.com/en/docs/api/geoapi/city-lookup/) |
| 日本語 | `ja` 対応。ただし指定言語がないデータは現地語、英語へfallbackする。`lang=ja` は全地名の日本語表記や、かな入力のヒットを保証しない。[Language](https://dev.qweather.com/en/docs/resource/language/) |
| 天気との接続 | GeoAPI はIDと緯度・経度を返す。都市ベースv7はIDまたは座標を受けるが、現行資料では廃止予定でv1を推奨。v1日次予報は `/weather/v1/daily/{latitude}/{longitude}`。保存をIDだけに固定する前に、座標解決と予報API版を判断する。[v7](https://dev.qweather.com/en/docs/api/weather/weather-daily-forecast-webapi-v7/)、[v1](https://dev.qweather.com/en/docs/api/weather/weather-daily-forecast/) |
| Host / 認証 | アカウント固有API Hostを使う。旧共有Hostは2026年から順次終了予定。JWTとAPI Keyに対応し、公式推奨はJWT。JWT秘密鍵等はサーバーで保持する構成を提案する。[API Host](https://dev.qweather.com/en/docs/configuration/api-host/)、[Authentication](https://dev.qweather.com/en/docs/configuration/authentication/)、[Security Guidelines](https://dev.qweather.com/en/docs/best-practices/security-guidelines/) |

外部リクエストの概念例は `https://{専用Host}/geo/v2/city/lookup?location={エンコード済み地名}&range=jp&lang=ja&number=10`。アプリの画面からこのURLを直接呼ばず、サーバー側adapterで認証を追加する。秘密鍵・API Keyを公開環境変数やブラウザbundleに入れない。日本語などはpercent-encodeし、空白は `%20` とする。[リクエストの最適化](https://dev.qweather.com/en/docs/best-practices/optimize-requests/)

## 検索と保存の操作案

1. ダイアログを開くと現在の地域を表示し、検索文字と選択候補をローカル状態に持つ。空入力では検索しない。
2. 初期案は「検索」ボタンまたはEnterで実行する。日本語IME変換中のEnterでは実行しない。自動補完にする場合はIME確定後のdebounceが必要だが、待ち時間は未決。
3. 検索中・候補あり・候補なし・通信失敗・一時的な利用制限を分ける。候補なしでは市区町村名を変える案内を出す。候補が最大件数に達した場合は全件が見えていると案内しない。
4. 検索条件を変えたら以前の候補選択を解除する。古い検索レスポンスが遅れて届いても現在の候補を上書きしない。閉じたダイアログに結果を反映しない。
5. 候補を選び「この地域に設定」で確定する案。候補選択だけでは保存しない。保存中は二重送信を防ぎ、成功後にホーム地域表示を更新する。保存失敗ならダイアログに選択を残し再試行可能にする。
6. 保存後、新地域の天気・自動推薦を読み直す。新地域の名前と旧地域の天気を組み合わせて表示しない。保存前のキャンセルでは既存地域とホーム表示を維持する。

汎用dialogとして初期フォーカス、フォーカス閉じ込め、Escape、閉じた後のフォーカス復帰を実装する。候補一覧はキーボードで選べる操作にする。既存 `ConfirmDialog` は削除確認用の `alertdialog` と固定文言構造であり、検索フォームをそのまま埋め込める部品ではない。[現行実装](../../apps/web/src/components/app/dialogs/ConfirmDialog.tsx)

## 実装境界案

| 境界 | 役割と既存コード |
| --- | --- |
| 検索API | アプリ内の検索APIが入力長・空入力・検索国を検証し、QWeather adapterを呼ぶ。画面へは候補ID・表示に必要な行政区域を返す。外部Hostや認証形式を公開契約にしない。パス・DTO・呼出上限は #276 で判断する。 |
| 地域設定API | ワードローブを対象に、選択した地域をサーバーで検証して保存する。ブラウザ由来の名称や座標を無検証で保存しない。既存は作成・取得のみで、更新APIを追加する必要がある。[FE endpoint](../../apps/web/src/api/endpoints/wardrobe.ts)、[BE repo](../../apps/api/src/domains/wardrobe/repo/wardrobeRepo.ts) |
| 永続化 | ワードローブの任意地域という合意に従う。候補は地点ID、表示名、行政区域、座標等だが、実際に保存できる項目と取得し直す項目は利用条件確認後に #274 / #276 で判断する。既存METAへの追加は候補に留める。[既存調査](天気連動テンプレート推薦_データモデルとアクセスパターン調査.md) |
| FE取得 | 現行Wardrobe DTOは名前のみであり拡張が必要。保存成功でWardrobe取得と新地域に依存する取得を更新する。ワードローブ・地域・対象日・モードのどれがquery keyに必要かは #276 に引き継ぐ。[schema](../../apps/web/src/api/schemas/wardrobe.ts)、[hooks](../../apps/web/src/api/hooks/wardrobe.ts)、[query keys](../../apps/web/src/api/queryKeys.ts) |

## 利用条件・運用上の制約

- GeoAPIと天気等は同じ料金区分で、確認時点では合計月50,000件まで単価0 CNY、その後は従量。GeoAPIだけの独立無料枠と見なさない。適用条件とアカウント設定は #273 / #274 で確認する。[料金](https://dev.qweather.com/en/docs/finance/pricing/)
- 429はQPM超過として待機・backoff対象。認証や不正入力の失敗を自動で繰り返さない。検索API側の上限と再試行方針を持つ。契約アカウントに適用される具体的QPM値は今回未確認。[最適化](https://dev.qweather.com/en/docs/best-practices/optimize-requests/)
- GeoAPIの一括保存・ダウンロード・独自インデックス化は禁止とされ、cache資料には永続保存に関する制限もある。全候補の蓄積による市区町村辞書化は採用しない。選択地域のどの情報をどの期間保存可能かは、ライセンス条件を確認してから決める。[利用制限](https://dev.qweather.com/en/docs/terms/restriction/)、[cache](https://dev.qweather.com/en/docs/best-practices/cache/)
- QWeather名と `https://www.qweather.com` へのリンクを見える形で表示する。検索ダイアログおよび天気表示の出典欄を実装案に含める。[Attribution](https://dev.qweather.com/en/docs/terms/attribution/)

## 接続検証で残る確認

| 担当 | 確認項目 |
| --- | --- |
| #273 | 専用Host・認証・GeoAPI利用可否。東京の区、政令市の区、一般市、町村を含む代表例と「府中」等の同名地名を検索し、名称・行政区域・座標・IDを確認。漢字、かな、市区町村接尾辞の有無、都道府県付き入力、`adm` の効き方を比較する。例はテスト入力候補であり、検索成功を確認した例ではない。 |
| #274 | v1 / v7の採用・日付境界・日本の服装指数提供状況、認証方式、上限・再試行、地域情報の保存許諾と天気cache運用。公式Language資料では指数の言語は中国語・英語のため、日本語表示を別途検討する。 |
| #276 | 検索・更新API、保存する識別子と座標/表示名、保存検証、query key、保存成功・失敗とタイムアウトの契約。 |
| #277 | 候補表示と検索・保存操作、該当なし・通信失敗の表示を試作で確認。モック候補は実GeoAPIで確認済みと表示しない。 |

本調査は地域検索UIの実現可能性と接続境界を整理したもの。QWeather採用の実接続検証完了、API契約確定、ホーム実装完了を意味しない。

## UI決定後の引き継ぎ（2026-10-09）

#277のユーザーレビューで、検索ボタン／Enter→候補選択→「この地域に設定」を採用した。また、ホーム天気欄の「天気情報：QWeather」リンクは削除する。上記の出典表示案は調査時の提案であり、ホームへのリンク配置は採用しない。出典条件と別の配置の整合は#274で判断する。地域検索ダイアログの出典表示は今回の削除指示に含まれない。
