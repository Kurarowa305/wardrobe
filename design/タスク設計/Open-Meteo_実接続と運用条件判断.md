# Open-Meteo の実接続・キャッシュ・運用条件（#274）

調査日: 2026-10-11（JST）。対象: [#274](https://github.com/Kurarowa305/wardrobe/issues/274)。関連: #271 / #272 / #276 / #277 / #288。

状態: **2026-10-11、ユーザーレビューにより接続・運用方針を確定**。ユーザーが「辞書更新機能は今回は不要・backlog優先度C」「天気キャッシュは当日中再利用」「その他は推奨でよい」と回答したため、以下を確定仕様とする。運用数値はwardrobe側の設定であり、提供元の保証値ではない。出典UIは天気欄右下の情報アイコン→出典ダイアログ。#288の指数ルールは変更しない。#274の判断は完了し、#276へ引き継げる。機能実装およびGitHubのIssueクローズはこの記録だけでは完了しない。

## 1. 確定した接続

バックエンドから `https://api.open-meteo.com/v1/forecast` を使用し、`models=best_match` を明示する。日本のJMAモデルも比較したが、特定モデルへの固定は採用しない。Best Match の実際の構成モデルは地域・期間・提供元更新で変わり得る。レスポンスから個別モデルが特定できたと扱わない。

現在のホームに必要な入力は次の1地点・1日・日次4変数で足りる。時間別5変数は今回の比較検証専用であり、本番では取得しない。current も取得しない。

```text
GET https://api.open-meteo.com/v1/forecast
  ?latitude={保存地域の予報用緯度・ABR近似利用は§8}
  &longitude={保存地域の予報用経度・ABR近似利用は§8}
  &models=best_match
  &daily=apparent_temperature_max,temperature_2m_max,temperature_2m_min,weather_code
  &timezone=Asia%2FTokyo
  &temperature_unit=celsius
  &timeformat=iso8601
  &start_date={リクエスト開始時のJST当日YYYY-MM-DD}
  &end_date={同日}
```

初回の3地点モデル比較は `forecast_days=1` で実行した。追加調査では自治体データの新宿区・檜原村代表座標と上記の `start_date=end_date=2026-10-11` を使用し、当日日次4項目を取得できた。[追加接続証拠](../調査データ/japan-municipality-274/forecast-from-abr.json)。日付固定に加え、応答採用直前にもJST当日を照合し、日付を跨いだ応答は新日の情報として採用しない。

日最高・日最低はJST 00:00〜翌00:00の予報モデルによる日次集計。現在の気温、観測された確定最高値、残り時間だけの予報に置き換えない。夜の表示も対象日全体の予報である。[Forecast仕様](https://open-meteo.com/en/docs)

## 2. 実データの証拠と限界

公開の代表座標のみを使用。ユーザーの保存地域・GPS・IP由来の地点・認証情報は使用しない。取得時刻、実URL、HTTP状態、応答JSONを [保存データ](../調査データ/open-meteo-274/responses.json) と [追加検索](../調査データ/open-meteo-274/search-additional.json) に保存した。50回中48回がHTTP 200、2回がTLS handshake timeout。通信失敗を0件検索やAPI欠損とは数えない。個別の接続時間はネットワーク環境依存で、SLA・本番p95を示さない。

次表は `daily.time=2026-10-11` の日最高体感温度 / 最高実気温 / 最低実気温（°C）/ 日次天気コード。観測・精度検証ではない。

| 公開代表地点（入力座標） | Best Match | JMA Seamless | JMA MSM | JMA GSM |
| --- | --- | --- | --- | --- |
| 東京 (35.68, 139.76) | 27.4 / 25.7 / 15.9 / 1 | 27.4 / 25.7 / 15.9 / 1 | 27.4 / 25.7 / 15.9 / 1 | 23.3 / 24.3 / 18.6 / 1 |
| 札幌 (43.06, 141.35) | 20.0 / 19.9 / 12.2 / 3 | 20.9 / 20.4 / 12.1 / 2 | 20.9 / 20.4 / 12.1 / 2 | 通信失敗、値は未確認 |
| 那覇 (26.21, 127.68) | 33.5 / 28.0 / 23.0 / 81 | 33.0 / 27.6 / 26.2 / 55 | 33.0 / 27.6 / 26.2 / 55 | 32.4 / 27.0 / 26.5 / 51 |

Best Match / JMA Seamless / JMA MSM の3地点では、日次4変数が有限数で、`timezone=Asia/Tokyo`、`utc_offset_seconds=32400`、温度単位 `°C` を確認した。時間別は当日00:00〜23:00の24行で、体感温度・実気温（°C）、相対湿度（%）、10m風速（`wind_speed_unit=ms`、m/s）、短波放射（W/m²）が取得できた。保存データ上の日最高体感温度は時間別体感温度の最大値と一致する。

JMA MSM は公式に約5km・時間別・3時間更新、GSMは約55km・6時間別を時間別へ補間・6時間更新とされる。更新周期はモデル投入周期であり、APIでの即時反映を保証しない。JMA限定では雷等の表現にも制約がある。[JMA仕様](https://open-meteo.com/en/docs/jma-api)

**資料と実応答の差:** JMA公式ページはGSMの放射由来の体感温度を利用不可と記載するが、東京・那覇のGSM実応答は体感温度が数値、短波放射が24行すべてnullだった。計算の内訳は確認できない。この差を「日射込みで利用できた」と解釈せず、GSM固定を避ける理由とする。Best Matchで日次体感温度が欠けた場合も#288のfallbackを適用する。

未検証: 季節ごとの継続的な予報精度、全自治体・離島、障害率、実配信遅延、モデル切替の計算内訳。モデル間の値の一致を採用モデルの証明や正確さの証明としない。

## 3. #288 / #276への入力契約

| 項目 | 入力契約 |
| --- | --- |
| 地域 | サーバー検証済みの自治体コード・表示名・行政区域・代表座標。ABRの元座標系EPSG:6668と予報用近似利用方針を保持する（§8）。予報応答の格子座標で保存地域を上書きしない |
| 日付 | `daily.time` とJST当日を照合。先頭行の決め打ちを避け、対象日の重複や配列不整合は応答を不採用 |
| 体感温度 | `daily.apparent_temperature_max`、返却単位 `°C`、有限数。丸めず#288の15/25°C境界へ渡す |
| 実気温 | `daily.temperature_2m_max/min`、各単位 `°C`。最高のみ季節fallbackに使える。現在気温で補完しない |
| 天気 | `daily.weather_code`、単位 `wmo code`。整数の既知コードだけ表示に変換する |
| メタデータ | provider、modelPolicy、targetDate、fetchedAt、取得済みデータの利用状態、判定根拠（体感由来／最高実気温fallback／手動が必要）を区別可能にする |

null・文字列・非有限数・単位不一致から数値を生成しない。有限な負の温度は正常値。日付と各配列長の不整合は新しい応答全体を不採用とする。日付対応が正しく体感温度だけ不正なら指数なし、最高実気温が有効なら#288の既存fallbackを使う。最低気温や天気だけの欠損で季節判定を追加しない。構造正常な新しい応答を受けた場合、その応答の欠損項目を旧応答からつぎはぎしない。

同地域・同JST日の検証済み応答は、取得失敗時に限らず当日中再利用する。別地域・前日情報を使わない。日付変更でautoへ戻すルールと記録日入力は独立する。DTO、欠損表現、表示丸め、キャッシュ無効化、状態遷移は#276で決定する。

## 4. 天気の画面表示方針

日次コードは当日の代表予報（公式定義では日中の最も厳しい天候）として使い、「現在の天気」や気象庁発表の天気と表現しない。表示名とアイコンは以下を基準に#276 / #282で固定する。

| WMOコード | 表示案 |
| --- | --- |
| 0 | 晴れ |
| 1, 2 | 晴れ時々曇り |
| 3 | 曇り |
| 45, 48 | 霧 |
| 51, 53, 55 | 霧雨 |
| 56, 57 | 凍る霧雨 |
| 61, 63, 65 | 雨 |
| 66, 67 | 凍る雨 |
| 71, 73, 75, 77 | 雪 |
| 80, 81, 82 | にわか雨 |
| 85, 86 | にわか雪 |
| 95, 96, 99 | 雷雨 |
| null / 不正 / 未知 | 天気不明（晴れに置換しない） |

最高・最低は同じ応答・同じ日付の実気温。コード欠損を体感温度欠損と混同しない。キャッシュ利用時は「取得済みの天気情報を表示」等で鮮度が分かる状態を#276へ渡す。[コードの一次資料](https://open-meteo.com/en/docs)

## 5. キャッシュ・障害・更新の確定方針

| 項目 | 初期値・扱い（wardrobe側の確定設定） |
| --- | --- |
| 予報キー | `open-meteo:forecast:v1:best_match:{regionId}:{latitude}:{longitude}:Asia/Tokyo:celsius:{YYYY-MM-DD}`。座標はサーバー保存値の正規化形式を固定し、丸めによる別地域の衝突を避ける |
| キャッシュ有効期限 | 取得した対象日のJST翌00:00。同地域・同JST日の有効な成功データは当日中再利用する。取得後3時間で再取得する処理は設けない |
| 同日再利用 | 同じ地域・座標・対象日の検証済みデータがあれば外部通信せず利用する。再表示・復帰・時間経過でも再取得しない。同日内にモデルが更新されても追随しない |
| 物理削除 | 翌00:00をexpiresAtとする。DB TTLの削除遅延に依存せず、読取時に対象日・地域・モデル方針を検査する |
| 取得タイミング | 画面を開く・復帰する・地域を保存する・JST日付が変わる時、同地域・当日データがなければ取得する。日付変更で前日データを無効化し、autoへ戻す。定期再取得・一斉更新は行わない |
| 重複抑止 | 同一キーの更新をサーバー全体でまとめる。Lambdaインスタンス内のメモリだけを共有キャッシュ／利用量管理とみなさない。短命ロック等の物理方式は#276へ |
| 外部通信予算 | 予報1回4秒。DNS/TLS/本文読取込みの中断可能な期限を設ける。ABR同梱案の検索・保存時に外部APIは呼ばない |
| 再試行 | 予報は同一操作内の自動再試行0回。クライアントQuery層・サーバー・SDKの隠れたretryも無効にする |
| 障害 | timeout、ネットワーク、5xx、JSON不正、構造不正は成功データを置換せず、同日キャッシュ→当日なしなら手動へ。404/400を繰り返さない |
| 再取得抑止 | 予報の更新失敗はキーごとに5分のcooldown。期間中は再アクセスでも外部通信せず同日キャッシュ／手動を返す。ABR同梱案の検索は配信済み辞書で処理し、外部送信はない |
| 429 | 自動で即再送しない。有効なRetry-Afterがあれば少なくともその期間、なければ5分、外部呼出を共有のprovider gateで停止する。既存同日データ／手動を返す。ABR検索は継続できる |
| 取得結果の競合 | 保存地域・対象日・検索世代が変わった後に届いた応答は旧コンテキストへ限定し、現在画面に採用しない |

#275のDB読取予算5秒と予報4秒は別。推薦API全体は初期10秒（DB5＋天気4＋残り1）を候補にし、直列／並列化とAPI入口からの残時間伝播を#276で確定する。天気期限切れでもDBの推薦処理を無期限に待たない。ホームへ戻るたびに「手動へ案内したから再試行」として外部通信を増やさない。

## 6. 無料利用と利用量の確定方針

無料APIは非商用に限定され、無料枠にSLAはない。今回の接続は登録・APIキー・認証なしで成功した。広告・課金・商用製品への組込みへ変更する場合は無料継続を前提にしない。データライセンスの利用許諾と、無料ホストの利用資格は別である。有料契約を自動で行わない。[料金](https://open-meteo.com/en/pricing)、[利用条件](https://open-meteo.com/en/terms)

公式公開枠は600 calls/分、5,000/時、10,000/日、300,000/月。Termsの「less than」を踏まえ、境界まで使わない。多変数・長期間・複数地点／モデルは1 HTTP=1 callとは限らない。今回の本番案は単一地点・1モデル・日次4変数・1日である。料金表に一部月間制限未施行の記載があっても、無制限として扱わない。

wardrobe全体の初期上限は **60回/分、600回/時、5,000回/日、150,000回/月**。Open-Meteoへの全試行（失敗を含む）を合算し、送信前に共有の永続カウンタで予約する。アプリ全体の外部送信を数える。ABR同梱案の検索・保存はこの枠を消費しない。将来Open-Meteoの別APIを追加しても同じ枠へ合算する。日・月はUTCで固定し、地域別JST日キャッシュと混同しない。分・時は直近60秒・3,600秒の移動窓、日・月は暦窓に加え直近24時間・31日の上限も守り、UTC境界の連続送信を防ぐ。カウンタを確認できない場合は外部送信を止める。

上限の80%到達を運用ログ／メトリクスへ記録し、100%で外部送信停止。同日予報キャッシュがなければ手動、地域検索は配信済みABR辞書を引き続き利用できる。共有IPで別アプリの通信が合算される可能性もあるため429も別途扱う。上限とレート計数方式は実装・負荷試験が必要で、今回実装済みではない。当日キャッシュでも利用数により枠を使い切るため、増加時は契約・利用方式を別途判断する。

QWeatherのAPI Host・JWT・秘密鍵配置／ローテーション・月50,000件枠は引き継がない。

## 8. 公開自治体データによる検索・保存方針（旧GeoNames保存案を更新）

デジタル庁の全国市区町村マスター、位置参照拡張、都道府県マスターを版固定してアプリに同梱する。名称と位置参照はそれぞれ1,918行で、コードの重複・結合漏れ・座標／読み欠損がないことを確認した。47都道府県、政令市とその区、東京都特別区、町村を含む。最新の全国自治体との全件照合・代表座標の現地精度確認は未実施。

- 地域検索はABR辞書に統一し、Open-Meteo検索の候補と混合しない。検索・保存のたびの外部通信、GeoNames IDの再解決、検索用無料API枠が不要になる。
- 安定IDは `abr:lg:{6桁lg_code}`。コードは先頭0を保つ文字列とする。地名・読みは検索キー、識別子はコード。都道府県・郡・市・区を区別し、同名自治体を自動で1件に決めない。
- NFKC・かな統一後、辞書の漢字・読み・行政区域付き名を検索する。漢字の行政接尾辞を省略した別名と前方／部分一致で「札幌」「しんじゅく」「ひのはら」を検索できる。かなを勝手に漢字変換しない。1文字の「津」も受け付ける。空入力・64文字超は候補なしの入力状態とする。
- 完全一致→前方一致→部分一致、同点はコード順。最大10件とhasMoreを返し、同名なら行政区域を表示してユーザーが選ぶ。市と区の両方に候補があることを保持する。
- 保存APIはクライアントのコードを同梱辞書で再解決し、存在・有効日・座標を検証する。名称や座標の申告値を信用しない。未知コード・辞書版不整合は再検索を案内し、別地域へ黙って移行しない。
- 保存する情報は source、lgCode、表示名・都道府県／郡／市／区、代表座標、sourceSrid、coordinatePolicy、datasetVersion、timezone=Asia/Tokyo、地域変更revision。変更・解除まで保持する。物理保存先とDTOは#276で確定する。
- 元座標はEPSG:6668（JGD2011）。WGS84と完全同一と記載せず、km単位の予報の代表点用途では経緯度をそのまま近似利用する方針（`jgd2011-as-wgs84-weather-v1`）。原座標系・座標を保存し、精密測位の変換として使わない。新宿区・檜原村で予報APIへの接続成功を確認したが、全地点の精度検証ではない。未知SRIDへ自動でこの近似を適用しない。
- 初回取得した辞書版をSHAで固定して同梱する。個人利用のため、辞書更新機能・定期更新確認は今回は実装しない。将来の更新機能は[backlogの優先度C](backlog.md)へ移した。取得時点と元データの更新時点は区別し、現在の固定辞書内で未知のコードは再検索へ案内する。

#277の検索ボタン／IME確定後Enter→候補選択→保存、保存前キャンセルで元を維持、保存失敗時は選択を保持する操作は維持する。検索元はABRに確定したが、機能実装ではない。[データの利用条件](https://www.digital.go.jp/policies/base_registry_address_tos)とCC BY 4.0互換の[PDL1.0](https://www.digital.go.jp/resources/open_data/public_data_license_v1.0)に従い、地域検索ダイアログにも提供元と加工主体を表示する。
