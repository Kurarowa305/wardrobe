# 最終着用日の整合性検証と監査（#278）

## 対象と確認結果

[#278](https://github.com/Kurarowa305/wardrobe/issues/278) と [取得整合性判断](./天気連動テンプレート推薦_取得整合性判断.md) に従う。

外部接続を使わない再現で、同日の履歴が2件あるときに1件削除すると、日別件数は1残るが最終着用日が0へ戻った。通常の服・テンプレート編集でも、記録更新前に取得した値で統計が上書きされた。さらに、削除処理が次点の日付を取得した後に別の履歴追加・削除が完了し、総件数が元へ戻ると、件数だけの競合検出は古い再計算結果を受け入れた。

## 実装

- 同日の日別件数を強整合で先に読み、2件以上なら最終着用日を維持する。1件で、削除日が最終着用日と一致するときだけ、その日より前のWearDailyをベーステーブルの強整合・降順Queryで取得する。
- 日別件数の減算・削除は、読み取った件数との一致を条件にする。対象日が欠落・0以下・整数以外ならCONFLICTとして履歴を保持する。
- 服・テンプレートに内部属性 `statsVersion` を追加する。履歴の作成・削除で統計と同じトランザクション内で1増やし、読み取り時の更新番号の一致を条件にする。未付与の既存項目は属性不存在を条件に、初回更新で1を保存する。公開DTOには追加しない。
- `wearCount` と `lastWornAt` の一致も検査する。更新番号により、別の追加・削除で両方が元に戻っても競合を検出できる。
- 通常編集は統計4属性（`wearCount` / `lastWornAt` / 対応する2つの索引ソートキー）を更新しない。既存の専用統計更新repoも更新番号を進め、処理中の読み取りを無効化する。
- 統計・日別件数の条件失敗、トランザクションの書き込み競合はCONFLICT（409）へ変換する。アプリケーションによる自動再送は追加しない。履歴先頭操作の条件失敗や、権限・容量・検証エラーを一律に競合へ変換しない。

前提は、保存済みの履歴・WearDaily・統計が監査で整合していること。実装修正だけでは既に壊れた値を修復しない。最大20服の記録上限の整合は #283 の範囲。

## 既存データの読み取り監査

`apps/api/scripts/audit-wear-stats.mjs` は読み取り専用。アプリのデフォルトテーブル名を流用せず、テーブルとレポート保存先を明示する。AWS SDK標準の認証チェーンを使い、秘密値は引数・レポートに出さない。必要な権限は対象テーブルの `dynamodb:Scan`。

```bash
AWS_PROFILE=your-profile pnpm --filter api audit:wear-stats \
  --table your-table --region ap-northeast-1 \
  --output /absolute/private/path/wear-stats-audit.json
```

全ページを強整合Scanで2回取得し、関連するキー・履歴・統計の指紋が一致した場合だけレポートを作る。Scan全体の同一時点スナップショットを保証するものではないため、補正判断は書き込み停止中の再監査を条件にする。関連項目をメモリに保持するため、テーブル規模・読み取り負荷を確認してから実行する。名前・画像・資格情報はレポートに含めず、識別用のキーと統計差分を保存する。ファイルは0600で新規作成し、既存ファイルを上書きしない。

履歴の記録時 `clothingIds` と `templateId` から日別件数、総着用回数、最終着用日、2つの索引キーを再計算する。論理削除済み対象と未着用対象も含む。構成服がない旧履歴や不正な日付、存在しない対象、重複キーは要調査とし、現在のテンプレートから過去の構成服を推測しない。

オフライン入力はDynamoDB属性型ラッパーを外した全項目のJSON配列を使う。部分エクスポートを監査の根拠にしない。

```bash
pnpm --filter api audit:wear-stats \
  --input /absolute/private/path/full-snapshot.json \
  --output /absolute/private/path/offline-audit.json
```

終了コードは0（整合）、2（差分または要調査）、1（取得・入力・出力失敗）。差分には対象キー、観測値、履歴に基づく期待値、観測した更新番号が含まれる。

## 不一致がある場合の補正手順

1. 修正版をデプロイし、旧バージョンの処理終了を待つ。対象への履歴・編集書き込みを停止し、バックアップを取得する。
2. 再監査し、キーごとの実測差分を確定する。`problems` がある場合は履歴の根拠を調査し、解決前に自動補正しない。
3. 各対象について、履歴から算出した日別件数の不足行を作成、誤った件数を更新、余分な行を削除する。統計4属性を期待値に揃え、`statsVersion` を1増やす。属性不存在と0は条件式上区別する。
4. 実行用の変更計画は、観測値・更新番号を条件に含めて別途レビューする。対象数がトランザクション上限を超える場合は書き込み停止を維持して分割し、途中失敗時は再監査から再開する。
5. 再監査の差分・要調査が0になったことを確認して書き込みを再開する。レポートやバックアップをGitへ追加しない。

本変更に補正実行機能は含めない。実データの対象キー・影響件数は本番監査後に確定する。
